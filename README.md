# ระบบเอเจนซี่นักแสดงและโมเดลลิ่ง (Casting Agency)

เว็บแอปเขียนด้วย **Python + Streamlit** เชื่อมกับ **MySQL** ตาม ER Diagram ของกลุ่ม
(PROJECT, ACTOR, SKILL, ACTOR_SKILL, ROLE, ROLE_SKILL, SCHEDULE, PAYMENT_INSTALLMENT และตารางใหม่ PORTFOLIO = 9 ตาราง ดูหัวข้อ 13)

ไฟล์นี้อ่านจบแล้วควรตอบได้ว่า: ทำไมเลือกวิธีนี้ / ต่อ database ยังไง / ปุ่มไหนดึงตารางไหน / เงื่อนไขตรงกับ ER ตรงไหน

## 1. ทำไมเลือก Streamlit + MySQL

- **เว็บแอป** เพราะมีผู้ใช้สองฝั่ง (นักแสดง / ผู้จัดงาน) เปิดจากเครื่องตัวเอง ข้อมูลอยู่ฐานข้อมูลกลางที่เดียว ตรงกับปัญหาในสไลด์ที่ข้อมูลกระจายอยู่ตามโซเชียล
- **Streamlit** เขียน Python อย่างเดียวได้ปุ่ม ตาราง ฟอร์ม ไม่ต้องแยกเขียน HTML/CSS/JavaScript และไม่ต้องมี server แยกอีกตัว โครงสร้างเลยเรียบง่ายพอที่จะอธิบายได้ทั้งหมด
- **MySQL** เพราะวิชา CSS222 ใช้ MySQL อยู่แล้ว (Sakila) และรองรับ foreign key, CHECK, transaction ที่ระบบนี้ต้องใช้
- **เขียน SQL เอง ไม่ใช้ ORM** เพื่อให้เห็นทุกบรรทัดว่าปุ่มไหนส่งอะไรไปที่ฐานข้อมูล

ลำดับการทำงานเมื่อกดปุ่มหนึ่งครั้ง:

```
ผู้ใช้กดปุ่มในเบราว์เซอร์
   -> Streamlit รันไฟล์หน้านั้นใหม่ (pages/xxx.py)
   -> หน้าเรียกฟังก์ชันใน queries.py
   -> queries.py เรียก db.py (query / execute / transaction)
   -> db.py ส่ง SQL ไปที่ MySQL ผ่าน connection pool
   -> ผลกลับมาเป็น list ของ dict -> หน้าเว็บแสดงผล
```

## 2. ติดตั้งและรัน (Windows)

ต้องมี 3 อย่าง: **Python 3.10 ขึ้นไป**, **XAMPP** (ได้ MySQL มาด้วย) และ **VS Code**

1. ติดตั้ง Python จาก python.org **ตอนติดตั้งให้ติ๊ก "Add python.exe to PATH"**
2. ติดตั้ง XAMPP แล้วเปิด **XAMPP Control Panel** กด **Start** ที่แถว **MySQL** ให้ขึ้นสีเขียว (ไม่ต้อง Start Apache ก็ได้)
3. แตกไฟล์ zip นี้ แล้วเปิดโฟลเดอร์ `casting-app` ใน VS Code
4. เปิด Terminal ใน VS Code (เมนู Terminal > New Terminal) แล้วพิมพ์ทีละบรรทัด:

```
pip install -r requirements.txt
python setup_db.py
streamlit run app.py
```

(ถ้า `pip` หรือ `python` ไม่รู้จัก ลองใช้ `py -m pip install -r requirements.txt` และ `py setup_db.py` แทน)

- `setup_db.py` สร้างฐานข้อมูล `casting_agency` พร้อมข้อมูลตัวอย่าง **และลบข้อมูลเก่าทิ้ง** ใช้ซ้ำได้ทุกครั้งที่อยากรีเซ็ตกลับเป็นข้อมูลตั้งต้น
- เบราว์เซอร์จะเปิดที่ `http://localhost:8501` เอง
- อยากได้ฐานข้อมูลเปล่า ไม่มีข้อมูลตัวอย่าง: `python setup_db.py --empty`
- ทางเลือก: จะ import `sql/schema.sql` แล้วตามด้วย `sql/seed.sql` ผ่าน phpMyAdmin (`http://localhost/phpmyadmin`) แทนก็ได้ ผลเหมือนกัน

### ถ้าเจอปัญหา

- **ต่อ MySQL ไม่ได้ / หน้าเว็บขึ้นกล่องแดง:** เช็กว่า MySQL ใน XAMPP เป็นสีเขียว ถ้าตั้งรหัสผ่านไว้ให้แก้ `password` ใน `config.py` ถ้าพอร์ตไม่ใช่ 3306 ก็แก้ `port`
- **`Unknown database 'casting_agency'`:** ยังไม่ได้รัน `python setup_db.py`
- **`streamlit` ไม่รู้จักคำสั่ง:** ใช้ `python -m streamlit run app.py`
- **`ModuleNotFoundError`:** ยังไม่ได้ `pip install -r requirements.txt` หรือติดตั้งผิด Python
- **พอร์ต 3306 ถูกใช้อยู่:** มี MySQL ตัวอื่นเปิดค้าง ปิดตัวนั้นก่อน หรือเปลี่ยนพอร์ตใน XAMPP

> หมายเหตุ: ระบบนี้ทดสอบอัตโนมัติกับ MariaDB 10.11 (ฐานข้อมูลตระกูลเดียวกับที่ XAMPP ให้มา) ยังไม่ได้ทดสอบกับ MySQL 8 จริง แต่ SQL ที่ใช้เป็นมาตรฐานทั่วไป

├─ bridge.py          ตัวกลาง: คำสั่งจากหน้าเว็บ -> เรียกฟังก์ชันใน queries.py / อ่านทุกตารางส่งกลับไปวาดหน้า

    ├─ test_logic.py  ทดสอบกฎธุรกิจกับ DB จริง 24 ข้อ
    ├─ test_bridge.py ทดสอบตัวกลางหน้าเว็บ <-> MySQL 14 ข้อ
    └─ test_pages.py  เปิดหน้าเว็บ (เวอร์ชัน classic) แล้วกดปุ่มจริงด้วย AppTest 15 ข้อ

**ทางเดินของข้อมูล:** ปุ่มในหน้าเว็บ (`ui/main.js`) → `app.py` (Streamlit รับคำสั่ง) → `bridge.py` → ฟังก์ชันใน `queries.py` → SQL → MySQL แล้ว `bridge.snapshot()` อ่านทุกตารางส่งกลับไปวาดหน้าใหม่ กฎธุรกิจจริงอยู่ฝั่ง Python ทั้งหมด (หน้าเว็บตรวจซ้ำอีกชั้นเพื่อแจ้งผลเร็ว) ท้ายทุกหน้ามีกล่อง "SQL ที่เพิ่งรัน" ให้ดูว่าปุ่มนั้นแตะตารางไหน

หมายเหตุ: ข้อมูลทุกตารางถูกส่งไปที่เบราว์เซอร์เพื่อวาดหน้า การ "ซ่อนโปรไฟล์" จึงซ่อนในหน้าเว็บและกันที่ฝั่งเซิร์ฟเวอร์ตอนเลือกเข้าบท (ถ้าต้องการซ่อนระดับข้อมูลจริง ให้ใช้เวอร์ชัน classic ที่กรองด้วย SQL)

หลักคิด: **หน้าเว็บไม่มี SQL เลย** ทุกอย่างผ่าน `queries.py` ถ้าอาจารย์ถามว่า "ปุ่มนี้ทำอะไรกับ database" ให้ดูกล่อง SQL ท้ายหน้า หรือดูชื่อคำสั่งใน `bridge.py` แล้วไปเปิดฟังก์ชันนั้นใน `queries.py`

## 4. เชื่อม database ยังไง (db.py)

1. `config.py` เก็บ host / port / user / password / ชื่อ database
2. `db.py` สร้าง **connection pool** ไว้ 5 เส้น (`@st.cache_resource` = สร้างครั้งเดียวทั้งแอป) แล้วหยิบมาใช้ซ้ำ ไม่ต้องเปิดปิด connection ใหม่ทุกครั้งที่กดปุ่ม
3. มี 3 ฟังก์ชันให้ `queries.py` เรียก:
   - `query(sql, params)` อ่านข้อมูล (SELECT) คืน list ของ dict
   - `execute(sql, params)` เขียนคำสั่งเดียว (INSERT/UPDATE/DELETE) คืนจำนวนแถวที่ถูกแก้
   - `with transaction() as tx:` เขียนหลายคำสั่งเป็นชุดเดียว จบปกติ = COMMIT, พังตรงไหน = ROLLBACK ทั้งชุด
4. ทุก SQL ใช้ `%s` เป็นช่องใส่ค่า (เช่น `WHERE actor_id = %s`) ไม่ต่อสตริงเอง ป้องกัน SQL injection
5. ทุกคำสั่งถูกจดลง SQL log เปิดสวิตช์ **"โหมดโชว์ SQL"** ที่ท้ายทุกหน้า แล้วดูได้ใต้สวิตช์นั้น (มีตัวกรองเฉพาะคำสั่งที่แก้ข้อมูล)

## 5. ปุ่มไหนดึง/แก้ตารางไหน

**ฝั่งนักแสดง** (เลือกว่าเป็นใครที่ dropdown ด้านบนของหน้า เพราะ ER ไม่มีตารางผู้ใช้/รหัสผ่านจึงไม่ทำ login)

- หน้า **แคตตาล็อกนักแสดง** → `search_actors` → SELECT ACTOR (กรองรูปลักษณ์/ทักษะใน SQL ชุดเดียว และเอาเฉพาะ `is_public = 1`) และปุ่ม **ดูโปรไฟล์** → `get_actor` + `get_actor_skills` + `list_works` → SELECT ACTOR, ACTOR_SKILL JOIN SKILL, PORTFOLIO
- ปุ่ม **สมัครเป็นนักแสดง** → `register_actor` → INSERT ACTOR (รวมคอลัมน์รูปลักษณ์ทั้งหมด) แล้ว INSERT ACTOR_SKILL หลายแถว (transaction เดียว) ตั้ง `is_public = 1` ให้เฉพาะเมื่อติ๊กเผยแพร่และมีทักษะอย่างน้อย 1 อย่าง
- ปุ่ม **บันทึกโปรไฟล์** → `update_actor` → UPDATE ACTOR, DELETE ทักษะเก่าใน ACTOR_SKILL, INSERT ทักษะใหม่ (ถ้าลบทักษะหมดและไม่มีผลงาน ระบบปิดโปรไฟล์ให้เอง)
- หน้า **โปรไฟล์และผลงานของฉัน** (`actor_profile.py`)
  - ปุ่ม **เผยแพร่โปรไฟล์ / ซ่อนโปรไฟล์** → `set_profile_public` → UPDATE ACTOR.is_public (เผยแพร่ได้เมื่อมีทักษะหรือผลงานอย่างน้อย 1 อย่าง ถ้าไม่ได้ใส่อะไรเลย กดไม่ได้)
  - ปุ่ม **บันทึกชื่อและแท็ก** → `update_actor` (ชื่อ, แนะนำตัว, ทักษะ)
  - ปุ่ม **เพิ่มผลงาน / บันทึกการแก้ไข / ลบผลงานนี้** → `add_work` / `update_work` / `delete_work` → INSERT / UPDATE / DELETE PORTFOLIO (แก้และลบได้เฉพาะผลงานของตัวเอง)
- หน้า **งานของฉัน** → `roles_of_actor` → SELECT ROLE JOIN PROJECT (รายละเอียดข้างในดึงจาก ROLE_SKILL, SCHEDULE, PAYMENT_INSTALLMENT)
- ปุ่ม **ยอมรับงาน / ปฏิเสธงาน** → `respond_to_role` → UPDATE ROLE.role_status (ต้องเป็นบทของตัวเองและสถานะยัง Selected) ถ้าปฏิเสธจะ UPDATE งวดที่ค้างเป็น Cancelled ด้วย
- หน้า **ตารางนัดของฉัน** → `schedule_of_actor` → SELECT SCHEDULE JOIN ROLE JOIN PROJECT
- หน้า **การจ่ายเงินของฉัน** → `payments_of_actor` → SELECT PAYMENT_INSTALLMENT JOIN ROLE JOIN PROJECT

**ฝั่งผู้จัดงาน**

- ปุ่ม **สร้างโปรเจกต์** → `create_project` → INSERT PROJECT
- ปุ่ม **บันทึก (เปลี่ยนสถานะโปรเจกต์)** → `update_project_status` → UPDATE PROJECT
- ปุ่ม **ค้นหานักแสดงที่เหมาะสม** → `find_matching_actors` + `explain_excluded` (รวมตัวกรองรูปลักษณ์ `traits`) → SELECT จาก ACTOR (กับ ACTOR_SKILL, ROLE, SCHEDULE ในเงื่อนไข) ยังไม่เขียนอะไรลง DB
- ปุ่ม **เลือกคนนี้** → `create_role` → transaction: ล็อกแถวนักแสดง, ตรวจเงื่อนไขซ้ำ, แล้ว INSERT ROLE, ROLE_SKILL, SCHEDULE, PAYMENT_INSTALLMENT
- ปุ่ม **ยกเลิกการจ้าง** → `cancel_role` → UPDATE ROLE เป็น Cancelled_by_Organizer และ UPDATE งวด Pending เป็น Cancelled (งวดที่จ่ายแล้วคงไว้เป็นประวัติ)
- ปุ่ม **บันทึกจ่าย** → `mark_paid` → UPDATE PAYMENT_INSTALLMENT เป็น Paid
- ปุ่ม **ค้นหา** (หน้าค้นหานักแสดง) → `search_actors` → SELECT ACTOR กรองพร้อมกันหลายเงื่อนไข
- หน้า **Dashboard** → `dashboard_numbers` → SELECT แบบ COUNT / SUM / GROUP BY

## 6. หัวใจของระบบ: จับคู่นักแสดง (queries.py → `find_matching_actors`)

นักแสดงที่ผ่านเกณฑ์ต้องครบ 3 ข้อ (ทำใน SQL ก้อนเดียว):

1. `actor_status = 'Active'`
2. **มีทักษะครบทุกข้อที่บทต้องการ** นับ `COUNT(DISTINCT skill_id)` ที่นักแสดงมีจากรายการที่ต้องการ แล้วเทียบว่าเท่ากับจำนวนที่ต้องการ (ถ้าบทไม่ระบุทักษะ ข้ามข้อนี้)
3. **ไม่มีคิวชน** ไม่มี SCHEDULE ของบทอื่น (ที่ยังเป็น Selected/Confirmed) ในวันเดียวกัน ที่เวลาซ้อนทับกัน ใช้สูตร `start_เดิม < end_ใหม่ AND end_เดิม > start_ใหม่` (เวลาที่ต่อกันพอดี เช่น เลิก 16:00 / เริ่ม 16:00 ไม่ถือว่าชน)

กดปุ่ม "ดู query ที่ใช้จับคู่ (SQL)" บนหน้าจะเห็น SQL จริง ส่วนแท็บ **"ถูกตัดออก"** บอกเหตุผลของทุกคนที่ไม่ผ่าน (ทักษะไม่ครบ / คิวชนกับงานไหน / Inactive)

**ทำไมตรวจคิวชนซ้ำอีกครั้งตอนกด "เลือกคนนี้":** ระหว่างที่ผู้จัดงานดูรายชื่ออยู่ อาจมีอีกคนเลือกนักแสดงคนเดียวกันตัดหน้า `create_role` จึงล็อกแถวนักแสดง (`SELECT ... FOR UPDATE`) แล้วตรวจใหม่ ใครมาทีหลังต้องรอ และจะเห็นบทที่คนแรกเพิ่งสร้าง (มีเทสข้อ 13 จำลองสี่คนแย่งนักแสดงคนเดียวกันพร้อมกัน สำเร็จได้แค่คนเดียวทุกรอบ)

## 7. เงื่อนไขในโค้ดตรงกับ ER ตรงไหน

- **CASTING** Project (0,N) — Role (1,1): `ROLE.project_id` เป็น NOT NULL + FK ไป PROJECT
- **ACTED_BY** Role (1,1) — Actor (0,N): `ROLE.actor_id` เป็น NOT NULL + FK ไป ACTOR **ทุกบทต้องมีนักแสดงเสมอ จึง INSERT ROLE ตอนเลือกคนแล้วเท่านั้น** รายชื่อที่ระบบคัดมาเป็นแค่ผลของ query ไม่มีตารางเก็บ (ถ้าจะให้เซฟบทที่ยังไม่มีคนได้ ต้องไปแก้ ER เป็น (0,1) ก่อน)
- **HAS_SKILL** Actor (0,N) — Skill (0,N): ตารางกลาง `ACTOR_SKILL` (PK คู่ actor_id + skill_id)
- **REQUIRES_SKILL** Role (0,N) — Skill (0,N): ตารางกลาง `ROLE_SKILL` บทที่ไม่มีแถวในตารางนี้เลย = ไม่ระบุทักษะ ระบบข้ามเงื่อนไขทักษะ
- **HAS_SCHEDULE** Role (0,N) — Schedule (1,1): `SCHEDULE.role_id` เป็น NOT NULL บทหนึ่งมี 0 นัดหรือหลายนัดก็ได้
- **HAS_PAYMENT** Role (1,N) — Payment (1,1): `PAYMENT_INSTALLMENT.role_id` เป็น NOT NULL ส่วนขั้นต่ำ "อย่างน้อย 1 งวด" ฐานข้อมูลบังคับเองไม่ได้ จึงคุมที่ `validate_installments` (ไม่มีงวดเลย = สร้างบทไม่ได้) และบังคับให้ยอดรวมงวดเท่ากับ `agreed_fee`
- ชื่อตารางและชื่อคอลัมน์ตรงกับสไลด์ "ตารางที่แปลงจาก ER Diagram" ทุกตัว

### ค่าสถานะที่ ER ไม่ได้กำหนด (ผมเลือกเอง ปรับได้)

ER ระบุแค่ว่ามีคอลัมน์สถานะ แต่ไม่ได้ระบุว่ามีค่าอะไรบ้าง ในระบบนี้ใช้:

- `role_status`: Selected (รอนักแสดงตอบ), Confirmed, Rejected_by_Actor, Cancelled_by_Organizer
- `payment_status`: Pending, Paid, Cancelled
- `actor_status`: Active, Inactive
- `project_status`: Open, In_Progress, Completed, Cancelled
- `event_type`: Shoot (ถ่ายทำ), Fitting (ฟิตติ้ง), Rehearsal (ซ้อม) ตามที่สไลด์เขียนไว้
- `gender`: Male, Female, Other, `skill_type`: Language, Performance, Physical, Other

ถ้ากลุ่มตั้งไว้ต่างจากนี้ ให้แก้ที่ `sql/schema.sql` (ส่วน CHECK) และ `config.py` (ป้ายภาษาไทย) ที่เดียวพอ

### วงจรสถานะของบท

```
Selected --(นักแสดงยอมรับ)--> Confirmed
Selected --(นักแสดงปฏิเสธ)--> Rejected_by_Actor
Selected หรือ Confirmed --(ผู้จัดงานยกเลิก)--> Cancelled_by_Organizer
```

บทที่เป็น Selected และ Confirmed เท่านั้นที่ "กินเวลา" ในปฏิทินนักแสดง ถ้าปฏิเสธหรือยกเลิก นักแสดงกลับมาว่างในช่วงนั้นทันที

### กฎการจ่ายเงิน

- จ่ายได้เฉพาะงวด Pending ของบทที่ **Confirmed** แล้ว (ไม่จ่ายให้คนที่ยังไม่ตอบรับ)
- กดจ่ายซ้ำไม่ได้: `UPDATE ... WHERE payment_status = 'Pending'` ครั้งแรกแก้ 1 แถว ครั้งที่สองไม่มีแถวตรงเงื่อนไข ระบบเลยปฏิเสธ
- "เลยกำหนด" ไม่ได้เก็บเป็นคอลัมน์ คำนวณตอน query: `payment_status = 'Pending' AND due_date < CURDATE()`

## 8. สคริปต์ demo 3-4 นาที

ข้อมูลตัวอย่างออกแบบไว้ให้ทุกกรณีมีให้ดู (วันที่ทั้งหมดอิงจากวันที่รัน `setup_db.py`)

1. หน้าแรก: ชี้ว่าตัวเลขแต่ละตารางนับสดจาก MySQL
2. เปิด **โหมดโชว์ SQL** ที่ท้ายหน้า
3. **ฝั่งนักแสดง → สมัคร:** สมัครนักแสดงใหม่ เลือกทักษะ แล้วดู SQL ที่ INSERT ACTOR และ ACTOR_SKILL
4. **ฝั่งผู้จัดงาน → สร้างบท + จับคู่:** ตั้งบทใหม่ ทักษะ **แสดงบทดราม่า + ภาษาอังกฤษ** ปล่อยตารางนัดตามค่าเริ่มต้น (วันนี้ + 7 วัน เวลา 09:00-17:00) กดค้นหา
5. ชี้แท็บ **"ถูกตัดออก"**: สมหญิงกับสมชายถูกตัดเพราะ **คิวชน** พิมพ์ใจถูกตัดเพราะ **Inactive** มาลีถูกตัดเพราะ **ขาดภาษาอังกฤษ**
6. กด **เลือกคนนี้** แล้วเปิดดู SQL ที่ INSERT 4 ตาราง
7. **ฝั่งนักแสดง → งานของฉัน:** เลือกชื่อคนที่ถูกเลือก กดยอมรับ
8. **ฝั่งผู้จัดงาน → งวดจ่ายเงิน:** กด **บันทึกจ่าย** แล้วลองเปิดหน้าใหม่ จะไม่มีปุ่มซ้ำ (ถ้าจะโชว์การกันจ่ายซ้ำ ให้อธิบายด้วย SQL `WHERE payment_status='Pending'` หรือรัน `tests/test_logic.py` ข้อ 11)
9. **จัดการบท:** ยกเลิกการจ้างบทหนึ่ง แล้วกลับไปดู dashboard ว่างวดที่ค้างถูกยกเลิกแล้ว

## 9. คำถามที่น่าจะโดนถาม

- **ทำไมเลือก Streamlit?** เขียน Python ภาษาเดียวได้เว็บที่ต่อ MySQL ได้ ไม่ต้องแยกเขียนหน้าเว็บกับ server ทำให้โครงสร้างเรียบง่ายและอธิบายได้ทั้งหมด
- **ต่อ database ยังไง?** `db.py` สร้าง connection pool จากค่าใน `config.py` แล้วเปิดฟังก์ชัน query / execute / transaction ให้ `queries.py` ใช้ ทุก SQL ใช้ `%s` ใส่ค่าแทนการต่อสตริง
- **ปุ่มค้นหานักแสดงตรวจคิวชนยังไง?** SQL มี `NOT EXISTS` ที่หา SCHEDULE ของบทอื่นของนักแสดงคนนั้นในวันเดียวกัน ที่ `start < end_ใหม่ AND end > start_ใหม่`
- **กันจ่ายซ้ำยังไง?** UPDATE มีเงื่อนไข `payment_status = 'Pending'` ถ้ามันเป็น Paid แล้วจะไม่มีแถวถูกแก้ ระบบดูจากจำนวนแถวที่ถูกแก้แล้วปฏิเสธ
- **ทำไม ROLE มี actor_id และ project_id?** เพราะความสัมพันธ์เป็นแบบหนึ่งต่อหลาย (1:N) FK ไปอยู่ฝั่ง "หลาย" คือ ROLE
- **ทำไมต้องมี ACTOR_SKILL และ ROLE_SKILL?** ความสัมพันธ์เป็น M:N ต้องแตกเป็นตารางกลางที่ PK เป็นคู่
- **ทำไมใช้ transaction?** สร้างบทต้องเขียน 4 ตาราง ถ้าพังกลางทางต้องไม่เหลือข้อมูลครึ่งๆ กลางๆ (เทสข้อ 9 จำลองกรณีพังกลางทางแล้ว ROLE ไม่ค้าง)
- **ถ้าสองคนเลือกนักแสดงคนเดียวกันพร้อมกันล่ะ?** `SELECT ... FOR UPDATE` ล็อกแถวนักแสดง คนที่สองต้องรอ แล้วตรวจคิวชนซ้ำจะเห็นบทที่คนแรกสร้าง จึงถูกปฏิเสธ
- **ทำไมไม่มี login?** ER ไม่มีตารางผู้ใช้ และขอบเขตในสไลด์ไม่รวมบัญชี-ภาษีนิติบุคคลและสัญญาจ้างเต็มรูปแบบ จึงใช้การเลือกชื่อจาก dropdown แทน
- **ทำไมไม่เก็บรายชื่อที่ระบบคัดมาเป็นตาราง?** ER กำหนดให้ทุกบทมีนักแสดงเสมอ (ACTED_BY เป็น (1,1)) รายชื่อคัดมาจึงเป็นผลของ query ณ เวลานั้น ซึ่งสดกว่าเก็บไว้ด้วย (ทักษะหรือคิวเปลี่ยนได้ตลอด)

## 12. เปิดดูบนมือถือ

เว็บนี้ทำให้แสดงผลบนมือถือได้ (เมนูพับเก็บ การ์ดและตารางปรับตามหน้าจอ) แต่ตัวโปรแกรมยังรันอยู่บนคอม มือถือแค่เปิดเบราว์เซอร์เข้ามาดู

**วิธีที่ 1: Wi-Fi เดียวกัน (ง่ายสุด ไม่ต้องติดตั้งอะไรเพิ่ม)**
1. เปิด MySQL ใน XAMPP
2. ดับเบิลคลิก `start.command` (Mac) หรือ `start.bat` (Windows) แทนการพิมพ์คำสั่งเอง
   - Mac ถ้าดับเบิลคลิกไม่ได้ ให้เปิด Terminal ที่โฟลเดอร์นี้แล้วพิมพ์ `chmod +x start.command` ครั้งเดียว
   - ถ้า Mac/Windows ถามเรื่อง Firewall ให้กด **Allow / อนุญาต**
3. ดูที่อยู่ที่ขึ้นในหน้าต่าง เช่น `http://192.168.1.45:8501` แล้วพิมพ์ในเบราว์เซอร์มือถือ (มือถือต้องต่อ Wi-Fi เดียวกับคอม)

**ถ้าเข้าไม่ได้:** Wi-Fi ของมหาวิทยาลัย/ร้านกาแฟมักบล็อกไม่ให้อุปกรณ์เห็นกัน ให้เปิด Hotspot จากมือถือ แล้วเอาคอมไปต่อ Hotspot นั้น แล้วเปิดเว็บใหม่ ที่อยู่จะเปลี่ยน ดูจากหน้าต่างอีกครั้ง

**วิธีที่ 2: ลิงก์ใช้ได้จากทุกที่ (ถ้าอยากส่งให้เพื่อน/อาจารย์เปิด)**
ติดตั้ง Cloudflare Tunnel ครั้งเดียว (Mac: `brew install cloudflared`, Windows: `winget install Cloudflare.cloudflared`) แล้วดับเบิลคลิก `share.command` (Mac) หรือ `share.bat` (Windows) จะเปิดเว็บและขอลิงก์ให้เลย หรือรันเองตอนที่เว็บเปิดอยู่:

    cloudflared tunnel --url http://localhost:8501

จะได้ลิงก์ `https://....trycloudflare.com` เปิดจากมือถือได้เลย ลิงก์ใช้ได้เฉพาะตอนคอมเปิดเว็บอยู่

**ข้อควรระวัง:** ระบบนี้ไม่มี login (ตาม ER ที่ไม่มีตารางผู้ใช้) ใครมีลิงก์ก็กดทุกปุ่มได้ เปิดเฉพาะตอนสาธิต แล้วปิดหน้าต่างเมื่อเสร็จ

## 13. สิ่งที่เพิ่มในรอบนี้ และต้องแก้ ER / สไลด์ให้ตรง

**ตาราง ACTOR เพิ่มคอลัมน์รูปลักษณ์** (เดิมมีแค่ `appearance_detail` เป็นข้อความอิสระ ค้นหาตามเงื่อนไขจริงไม่ได้) คอลัมน์เดิมทั้งหมดยังอยู่ ไม่ได้ลบหรือเปลี่ยนชื่อ

- ข้อมูลพื้นฐาน: `birth_date`, `province`, `experience_level` (Beginner/Intermediate/Professional), `can_travel`
- สัดส่วน: `height_cm`, `weight_kg`, `bust_chest_cm`, `waist_cm`, `hip_cm`, `shoe_size_eu`, `clothing_size` (XS-XXL), `body_type` (Slim/Athletic/Average/Curvy/Plus_Size/Muscular)
- ลักษณะ: `skin_tone`, `hair_color`, `hair_length`, `hair_texture`, `eye_color`, `has_tattoo`, `has_piercing`
- ทุกคอลัมน์ที่เป็นชุดค่า (enum) มี CHECK constraint ใน `schema.sql` และช่วงตัวเลขมี CHECK เช่น ส่วนสูง 100-230
- **อายุต้อง 18 ปีขึ้นไป** ตรวจในโค้ด (`clean_profile` ใน queries.py) ไม่ได้ใช้ CHECK เพราะ CHECK ใช้ `CURDATE()` ไม่ได้ ให้บอกอาจารย์ตามนี้

**ตาราง SKILL** มี `skill_type` ใหม่คือ `Modeling` (งานโมเดลลิ่ง) รวมเป็น 5 หมวด และมีทักษะ 89 อย่าง (เดิม 12)
ตารางไม่เพิ่ม ไม่ลด และความสัมพันธ์ (ACTOR_SKILL, ROLE_SKILL ฯลฯ) เหมือนเดิม จึงต้องไปเพิ่มคอลัมน์ในรูป ER/Relational schema ที่ใช้ส่งงานด้วย

**ตัวกรองรูปลักษณ์** (`traits`) ใช้ได้ที่ 3 หน้า: แคตตาล็อก, ค้นหานักแสดง, สร้างบท + จับคู่ ทุกเงื่อนไขเป็น AND ใน SQL เดียวกับทักษะและเช็กคิวชน (`_traits_sql` ใน queries.py)
คนที่ถูกตัดออกจากการจับคู่ยังมีเหตุผลบอกครบ รวมเหตุผลด้านรูปลักษณ์ เช่น "ส่วนสูง 165 ซม. ต่ำกว่า 175" (`trait_failures`)

**ภาพนักแสดง** ไม่ใช่รูปถ่ายจริง แต่วาดจากคอลัมน์รูปลักษณ์ด้วย `art.py` (ER ไม่มีคอลัมน์รูป และเลี่ยงเรื่องสิทธิ์ภาพ) นักแสดงทุกคนในข้อมูลตัวอย่างเป็นบุคคลสมมติ

**โปรไฟล์สาธารณะและผลงาน (รอบล่าสุด)**

- **ACTOR เพิ่ม 2 คอลัมน์:** `bio` (แนะนำตัวสั้นๆ ไม่เกิน 500 ตัวอักษร) และ `is_public` (BOOLEAN ค่าเริ่มต้น 0 = ซ่อน)
- **ตารางใหม่ PORTFOLIO** (ผลงานของนักแสดง) ความสัมพันธ์ ACTOR (1,1) — HAS_WORK — PORTFOLIO (0,N)
  - คอลัมน์: `work_id` (PK), `title`, `work_type` (Film/Series/Commercial/Runway/Photoshoot/Music_Video/Stage/Online/Other), `role_played`, `work_year`, `description`, `link_url`, `actor_id` (FK → ACTOR, ON DELETE CASCADE)
  - CHECK: `work_type` อยู่ในชุดค่าที่กำหนด, `work_year` 1980-2100 (ไม่ให้เกินปีหน้าตรวจในโค้ด เพราะ CHECK ใช้ปีปัจจุบันไม่ได้)
  - ใช้ตารางแยก ไม่ยัดเป็นข้อความก้อนเดียวใน ACTOR เพราะนักแสดง 1 คนมีผลงานได้หลายชิ้น (ไม่ให้ผิด 1NF) จำกัด 20 ชิ้นต่อคนในโค้ด (`MAX_WORKS`)
- **กฎการมองเห็น:** ผู้จัดงานเห็นนักแสดงก็ต่อเมื่อ `is_public = 1` เท่านั้น ใช้กับแคตตาล็อก ค้นหา จับคู่ หน้าแรก และรายชื่อ "ใครถูกตัดออก" ทุกจุดกรอง `a.is_public = 1` ใน SQL
  - `create_role` ตรวจซ้ำใน transaction ด้วย ต่อให้ยิงตรงมาโดยไม่ผ่านหน้าเว็บก็เลือกคนที่ซ่อนอยู่ไม่ได้
  - `is_public` ตั้งเป็น 1 ได้เมื่อมีชื่อ **และ** มีทักษะหรือผลงานอย่างน้อย 1 อย่าง (`set_profile_public` ตรวจ) ถ้าไม่ได้ใส่อะไรเลย คนอื่นจะไม่เห็น
  - ถ้าลบทักษะ/ผลงานจนหมด ระบบตั้ง `is_public` กลับเป็น 0 เอง (`_sync_visibility`) กฎนี้จึงไม่หลุดแม้แก้ข้อมูลทีหลัง
  - dropdown "คุณคือนักแสดงคนไหน" ยังเห็นทุกคนรวมคนที่ซ่อนอยู่ (มีป้าย [ยังไม่เผยแพร่]) ไม่งั้นเจ้าของจะเข้าไปแก้โปรไฟล์ตัวเองไม่ได้
- ข้อมูลตัวอย่าง: นักแสดง 36 คนแรกเผยแพร่แล้วและมีผลงาน 110 ชิ้น (ชื่อผลงานและแบรนด์สมมติทั้งหมด) ส่วน #37 นภัส และ #38 ธีรพล เป็นผู้สมัครใหม่ที่ยังไม่ได้ใส่อะไร จึงไม่โผล่ที่ฝั่งผู้จัดงาน ใช้โชว์กฎนี้ตอน demo ได้ (เลือกชื่อเขาที่หน้า "โปรไฟล์และผลงานของฉัน" แล้วลองเพิ่มผลงาน/แท็กและกดเผยแพร่)
- ข้อความที่ผู้ใช้พิมพ์ (ชื่อผลงาน รายละเอียด ลิงก์) ผ่าน `esc()` ก่อนใส่หน้าเว็บทุกจุด และลิงก์รับเฉพาะ `http://` / `https://` (ตรวจทั้งตอนบันทึกและตอนแสดงผล)

## 14. แชร์ให้เพื่อนดู

- เว็บจริง (Streamlit + MySQL) รันบนเครื่องคุณ ให้เพื่อนเปิดผ่านลิงก์ได้ด้วย `share.command` / `share.bat` (ดูหัวข้อ 12 วิธีที่ 2) ต้องเปิดคอมค้างไว้ และเพื่อนจะกดได้ทุกปุ่มเพราะไม่มี login
- ถ้าอยากได้ลิงก์ที่เปิดได้ตลอดโดยไม่ต้องเปิดคอม ต้องย้ายฐานข้อมูลและแอปไปโฮสต์ออนไลน์ ซึ่งเป็นขั้นตอนแยก (เช่น Streamlit Community Cloud + MySQL บนคลาวด์) ไม่ได้รวมในโปรเจกต์นี้
- ส่งลิงก์หน้าแรก (ไม่มี path ต่อท้าย) ให้เพื่อน อย่าส่งลิงก์ลึก เช่น `.../actor_profile` เป็นคนแรกหลังเพิ่งเปิดเซิร์ฟเวอร์ เพราะ Streamlit จะเปิดไฟล์หน้านั้นตรงๆ โดยไม่ผ่านเมนูและธีม (เปิดหน้าแรกสักครั้งหลังสตาร์ทก็หายแล้ว)
